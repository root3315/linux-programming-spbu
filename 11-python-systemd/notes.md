# Python и systemd

## Когда bash уже мало

В лекции 03 уровни в журнале считались конвейером `cut -d' ' -f1 app.log | sort | uniq -c | sort -nr`.
Пока задача такая, конвейер лучше всего: читается сразу, ставить ничего не надо. Переписывать его
на Python незачем.

Python нужен, когда появляется «если»: посчитать два файла и сравнить, сохранить результат в JSON,
проверить сайт и записать время ответа, не упасть на пустом файле. Правило с лекции: одна-две
команды — bash, ветвления, файлы и форматы — Python, расписание — systemd. Смешивать можно: Python
вызывает `grep`, bash запускает Python-скрипт.

Чем Python удобнее для таких задач:

- числа остаются числами: в bash `[[ "10" > "9" ]]` ложь, строки сравниваются по буквам, а в
  Python `10 > 9` правда;
- есть список `["INFO", "ERROR"]` и словарь `{"INFO": 3}`, счётчик и группировка пишутся в строку;
- в стандартной библиотеке уже есть JSON, даты, пути, HTTP: `import json, pathlib, urllib`.

Минусы тоже есть: для простой задачи код длиннее, и нужен интерпретатор. В Ubuntu 24.04 он уже
стоит, `python3 --version` даёт 3.12.3.

## Python: что надо помнить

```python
#!/usr/bin/env python3
name = "школа"
print(f"Привет, {name}!")
```

Первая строка — shebang, как в лекции 03, с ним файл запускается через `chmod +x hello.py && ./hello.py`.
Без него работает `python3 hello.py`. `f"...{name}..."` подставляет значение в строку.

Блоки задаются отступом в 4 пробела, без `{ }` и `;`. Это синтаксис, а не стиль: сдвинул строку не так,
и программа не запустится.

Счётчик уровней на Python — словарь, у которого отсутствующий ключ сразу равен нулю:

```python
from collections import Counter
levels = Counter()
for line in f:
    levels[line.split()[0]] += 1
print(levels.most_common())   # [('INFO', 3), ('ERROR', 3), ('WARN', 2)]
```

`most_common()` сортирует по убыванию, при равенстве оставляет порядок, в котором ключи появились.

### Аргументы: argparse

```python
parser = argparse.ArgumentParser(description="Счётчик уровней")
parser.add_argument("file")
parser.add_argument("--top", type=int, default=0)
args = parser.parse_args()
```

За эти строки получаю `--help`, проверку типа и понятную ошибку: `--top два` даёт
`error: argument --top: invalid int value: 'два'` и код 2. Свою ошибку можно выдать так же через
`parser.error(...)`.

### Ошибки и код возврата

```python
try:
    levels = count_levels(args.file)
except FileNotFoundError:
    print(f"нет такого файла: {args.file}", file=sys.stderr)
    return 1
```

Ошибку ловим и выходим с кодом 1, а не падаем со стеком вызовов. Сообщение пишем в stderr. Код
возврата важен: 0 — успех, не 0 — ошибка. По нему CI (лекция 07) и systemd решают, всё ли хорошо.
В конце файла `sys.exit(main(sys.argv[1:]))`, тогда то, что вернула `main`, становится кодом процесса.

Деление на ноль надо проверять самому: на пустом журнале `total = 0`, и `count / total * 100`
упадёт с `ZeroDivisionError`.

### Проверка сайта: три исхода

```python
try:
    with urllib.request.urlopen(url, timeout=5) as r:
        return r.status, elapsed()
except urllib.error.HTTPError as e:     # сервер ответил, но 404, 500...
    return e.code, elapsed()
except urllib.error.URLError as e:      # не ответил вообще
    return None, str(e)
```

Сайт ответил хорошо, ответил ошибкой или не ответил. Их нельзя путать: `HTTPError` — тоже ответ, у
него есть код. `HTTPError` — подкласс `URLError`, поэтому его `except` должен стоять первым. Время
меряют через `time.monotonic()`, а не `time.time()`: монотонные часы не прыгают, если поменяли
системное время. По сути это тот же `connect`, `read`, `close` из лекции 09, только руками их
писать не надо.

### Опасное в два шага

`rename.py` из архива без `--apply` только печатает план: что во что переименует. Выполняет только с
флагом. Так стоит делать любую массовую операцию с файлами.

## systemd

systemd — первый процесс, PID 1. Его запускает ядро, а он запускает всё остальное: службы,
терминалы, таймеры. Проверка: `ps -p 1 -o comm=` печатает `systemd`. С лекции запомнил аналогию:
вахтёр, который открывает здание, следит за порядком и записывает в журнал, кто пришёл и ушёл.

Три слова:

- unit — описание одной вещи (службы, таймера, точки монтирования), текстовый файл;
- service — программа, которая работает постоянно или отрабатывает один раз;
- timer — расписание, когда запускать service.

Вывод программ systemd пишет в общий журнал, его читает `journalctl`.

### Юнит-файл службы

```ini
[Unit]
Description=Подсчёт уровней в журнале

[Service]
Type=oneshot
WorkingDirectory=/home/stepan/auto-lab/Chapter11
ExecStart=/usr/bin/python3 python/logsum.py python/app.log
```

`[Unit]` — что это, `[Service]` — что запускать, `[Install]` — когда включать (у службы, которую
будит таймер, его можно не писать). `Type=oneshot` — отработал и вышел, как скрипт. `Type=simple` —
работает постоянно, как сервер, к нему часто добавляют `Restart=on-failure`.

> **Грабли:** systemd режет `ExecStart` по пробелам. Путь `~/auto-lab/my lab/logsum.py` без
> кавычек превращается в два аргумента, и python3 пишет `can't open file '/home/stepan/auto-lab/my'`.
> `systemd-analyze verify` такое не ловит, ошибка видна только при запуске. Путь с пробелом в
> `ExecStart` берут в кавычки. В `WorkingDirectory` наоборот: кавычки станут частью пути.

Полезное в юнитах: `%h` — домашний каталог, `%S` — `~/.local/state` у пользовательских юнитов.
`EnvironmentFile=` читает переменные из файла, а `${VAR}` в `ExecStart` подставляется одним
аргументом.

### Таймер

```ini
[Unit]
Description=Запускать подсчёт по расписанию

[Timer]
OnCalendar=*:*:00
AccuracySec=1s
Persistent=true

[Install]
WantedBy=timers.target
```

`logsum.timer` сам находит `logsum.service` по имени. `Persistent=true` — если машина была
выключена в нужное время, запуск пройдёт сразу после включения. Время последнего запуска
хранится в `~/.local/share/systemd/timers/stamp-<имя>.timer`.

Расписание `OnCalendar`:

| Строка | Когда |
| --- | --- |
| `*:*:00` | каждую минуту в 0 секунд |
| `*-*-* 03:00:00` | каждый день в 3:00 |
| `Mon..Fri 09:00` | по будням в 9:00 |
| `hourly`, `daily`, `weekly` | готовые слова |

`systemd-analyze calendar "*-*-* 03:00:00"` показывает следующий запуск, ничего не запуская.

> **Грабли:** по умолчанию `AccuracySec=1min`: systemd может сдвинуть запуск почти на минуту, чтобы
> будить процессор реже. Для таймера раз в минуту это выглядит так, будто он не сработал. На
> занятии ставили `1s`, и в журнале запуск ровно в `:00`.

### Команды

```bash
systemctl --user daemon-reload               # перечитать юниты после правки
systemctl --user start logsum.service        # запустить сейчас
systemctl --user status logsum.service
systemctl --user enable --now logsum.timer   # включить и запустить
systemctl --user list-timers                 # когда следующий запуск
journalctl --user -u logsum.service -n 20    # что было в журнале
systemctl --user disable --now logsum.timer  # выключить
```

`--user` обязательно: без него systemctl работает с системными службами, а там нужен root. Свои
юниты лежат в `~/.config/systemd/user`. `start` — запустить прямо сейчас, `enable` — запускать при
старте (для таймера это значит «завести будильник»), `enable --now` — то и другое.

У oneshot-службы после работы `Active: inactive (dead)` и `status=0/SUCCESS`. Это нормально:
служба сделала дело и вышла. Плохо, когда `failed`: если программа вернула не 0, systemd пишет
`Failed with result 'exit-code'`, а `systemctl start` тоже возвращает 1.

`systemd-analyze --user verify файл.service` проверяет синтаксис до запуска.

## Порядок, которого держусь

1. Скрипт сначала руками, с понятным кодом возврата.
2. Пути в юните абсолютные, с пробелами в кавычках.
3. Один раз `systemctl --user start` и посмотреть журнал. Только потом `enable --now` таймера.
4. `systemd-analyze calendar`, чтобы не ждать сутки не того запуска.
5. История в `journalctl --user -u имя -n 50`.
6. После занятия `disable --now` и удалить юниты, иначе через месяц не вспомнить, чей таймер.

Схема целиком: таймер будит службу, служба запускает скрипт, скрипт считает и возвращает код,
вывод и ошибки лежат в журнале.

## Вопросы с лекции

- Почему `inactive (dead)` у oneshot нормально? Потому что служба и должна завершиться. Успех
  видно по `status=0/SUCCESS`.
- Зачем `AccuracySec` и почему минута? systemd собирает близкие по времени запуски вместе, чтобы
  будить машину реже. На ноутбуке это экономит батарею.
- cron или таймер? cron проще, если нужна одна строка в crontab. У таймера есть журнал, `status`,
  догон пропущенного запуска (`Persistent=true`), запуск вручную через `start` и проверка
  расписания через `systemd-analyze calendar`.
