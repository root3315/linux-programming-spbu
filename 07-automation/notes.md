# Автоматическая сборка

## Идея занятия

Сборку, тесты и пакет должен делать скрипт, а не человек по памяти: тогда они одинаковые на
любой машине и не пропускаются. Цепочка такая: изменил код, `git push`, CI собрал и прогнал
тесты, появился пакет. Красный CI — нормально, плохо, когда его никто не замечает.

## Git: три области

Git хранит снимки, а не разницу: каждый коммит — полное состояние дерева плюс ссылка на
родителя. Поэтому сравнить любые две версии дёшево, а ветки почти ничего не стоят.

Файл проходит три места: рабочий каталог → `git add` → индекс → `git commit` → история
(`HEAD`). Коммит — снимок индекса, а не каталога, поэтому можно закоммитить часть изменений.

```text
$ echo "// a" >> src/main.c; echo "// b" >> src/greet.c
$ git add src/greet.c
$ git status --short
M  src/greet.c
 M src/main.c
$ git diff --stat
 src/main.c | 1 +
 1 file changed, 1 insertion(+)
$ git diff --staged --stat
 src/greet.c | 1 +
 1 file changed, 1 insertion(+)
```

`git diff` — каталог против индекса, `git diff --staged` — индекс против `HEAD`. В
`status --short` левая колонка — индекс, правая — каталог: `M ` уже в индексе, ` M` ещё нет,
`??` не отслеживается, `UU` конфликт.

Забыл `add` — файла нет в коммите. Забыл `commit` — изменения только у меня.

## Ветки, слияние, конфликт

Ветка — подвижная ссылка на коммит. `git switch -c feature/x` записывает одно имя, файлы не
копируются.

```bash
git switch -c feature/greet     # правим, коммитим
git switch main
git merge feature/greet         # Fast-forward, если в main ничего не менялось
git branch -d feature/greet
```

Fast-forward: `main` просто переезжает вперёд, ветки в графе не видно. `git merge --no-ff`
всегда делает коммит слияния с двумя родителями.

Конфликт бывает, когда обе ветки изменили одни и те же строки. Git не решает за меня и
оставляет в файле оба варианта:

```text
<<<<<<< HEAD
    snprintf(buffer, sizeof buffer, "Hello there, %s!", name);
=======
    snprintf(buffer, sizeof buffer, "Hi, %s!", name);
>>>>>>> feature/greet
```

Сверху моя ветка (`HEAD`), снизу входящая. Порядок:

1. `git status` — какие файлы в конфликте (`UU`).
2. Оставить нужный вариант (можно третий), убрать маркеры.
3. `git add файл` — «решено».
4. `git commit` — слияние закончено. Передумал — `git merge --abort`.

> **Грабли:** забытые маркеры. `git diff --check` их находит (`leftover conflict marker`,
> код 2), а gcc пишет `error: version control conflict marker in file`. Проверять до `add`.

## .gitignore

В репозитории только то, что нельзя восстановить. Всё, что делает сборка (`hello`, `*.o`,
тестовые бинарники, `*.deb`, `gmon.out`), восстанавливается одной командой. Проверка перед
коммитом — `git status --short`: артефактов там быть не должно. В примере с занятия в
`.gitignore` не было `build/`, куда `build-deb.sh` раскладывает пакет, и после первого же
`./ci.sh` он вылез в `status`.

Хуже всего закоммитить секрет: `.env`, ключ, токен. `git rm --cached файл` убирает его из
индекса, но история хранит всё. Для секрета один выход — сменить ключ.

## git bisect

Двоичный поиск коммита, после которого всё сломалось: каждый шаг отбрасывает половину.
Восемь коммитов — три проверки, тысяча — десять.

```bash
git bisect start HEAD <хороший-коммит>
git bisect run ./ci.sh      # 0 — хороший, 125 — пропустить, остальные 1..127 — плохой
git bisect reset
```

Условие — история рабочая: в хорошей точке всё собирается. И проверка должна быть полной. У
меня `git bisect run make test` пропустил сломанный `main.c`: цель `test` его не собирает.

## CI

Человек забывает, CI запускается на каждый коммит. Что это даёт: сборка с нуля в чистой
среде, без моих локальных файлов; зелёная галочка как факт, а не обещание; видно, какой
коммит всё сломал; пакет собирается сам. Любой шаг упал — дальше не идём.

### ci.yml

Файл `.github/workflows/ci.yml`:

| Ключ | Смысл |
|---|---|
| `on` | когда запускать: `push`, `pull_request`, можно с фильтром `paths` |
| `jobs` | набор задач, идут параллельно |
| `runs-on` | образ машины, например `ubuntu-24.04` |
| `strategy.matrix` | варианты, например `cc: [gcc, clang]` |
| `steps` | шаги внутри задачи по порядку |
| `uses` | готовое действие: `actions/checkout@v4`, `actions/upload-artifact@v4` |
| `run` | команда оболочки |

Матрица — не цикл: каждый вариант идёт на отдельной машине и отдельно отмечается. Упал один —
задача красная. `${{ matrix.cc }}` — подстановка значения.

Порядок шагов важен: тесты без сборки бессмысленны, пакет без тестов тоже. Частая ошибка —
шаг `make test` без шага `make`: локально работает, потому что бинарник уже собран, в чистой
среде падает.

### ci.sh

Те же шаги в скрипте запускаются локально, без аккаунта и сети. `ci.sh` и `ci.yml` не должны
расходиться, проще всего, когда `ci.yml` просто вызывает `ci.sh`.

```sh
set -eu
make clean
make CC="$CC_ARG"
make test CC="$CC_ARG"
./packaging/build-deb.sh
```

`set -e` — выйти на первой упавшей команде, `set -u` — ошибка на неопределённой переменной.

> **Запомнить:** CI смотрит на код возврата, а не на текст. Цепочка такая: тест вернул 1,
> make написал `Error 1` и сам вышел с 2, `ci.sh` с `set -e` остановился и вернул 2. Без
> `set -e` скрипт идёт дальше, собирает пакет из сломанного кода и возвращает код последней
> команды, то есть 0.

Тест, который всегда возвращает 0, бесполезен.

## Пакет .deb

Бинарник — это просто файл. Пакет говорит, куда ставить, что нужно для работы, какая версия
и как удалить ровно то, что поставили. Пакетный менеджер ведёт учёт файлов, скопированный
руками файл он не знает и не уберёт.

Внутри `.deb` — `ar`-архив: `debian-binary`, `control.tar.*` и `data.tar.*` (в Ubuntu 24.04
сжаты zstd). В `data` пути от корня будущей системы: `./usr/bin/hello`, а не `/usr/bin/hello`.

`DEBIAN/control`, паспорт пакета:

```text
Package: hello
Version: 1.1.0
Section: utils
Priority: optional
Architecture: amd64
Maintainer: Имя <почта>
Depends: libc6 (>= 2.34)
Description: учебная утилита приветствия
 Строка с пробелом в начале — расширенное описание.
```

- `Version` — по ней сравниваются версии;
- `Architecture` — `amd64`, `arm64`, `all` для скриптов;
- `Depends` — что должно стоять до установки;
- `Maintainer` — обязательное поле.

Без пробела в начале строки после `Description:` `dpkg-deb` не разберёт файл. Версия по
схеме MAJOR.MINOR.PATCH: 1.0.0 первый выпуск, 1.1.0 новая возможность, 1.1.1 исправление,
2.0.0 несовместимое изменение.

### DESTDIR и сборка без root

`DESTDIR` — корень «будущей системы». `make install DESTDIR=build/deb PREFIX=/usr` кладёт файлы
в `build/deb/usr/bin`, а не в настоящий `/usr`. Дальше `control` в `build/deb/DEBIAN/` и
`dpkg-deb --root-owner-group --build build/deb dist/hello_1.1.0_amd64.deb`. Без
`--root-owner-group` в пакете будет мой пользователь вместо `root/root`. `make install` без
`DESTDIR` на учебной машине не делать: файлы разлетятся по системе.

Проверка без установки (`dpkg -i` требует root):

```bash
dpkg-deb -c pkg.deb                  # содержимое: пути, права, владелец
dpkg-deb -I pkg.deb                  # заголовок: Version, Depends
dpkg-deb -f pkg.deb Version          # одно поле
dpkg-deb -x pkg.deb /tmp/pkg         # распаковать и запустить /tmp/pkg/usr/bin/hello
```

> **Грабли:** версия в нескольких местах. В примере с занятия она была в `Makefile`, в
> `control` и в `build-deb.sh`, а работала только последняя. Версия в коде, в `control` и в
> имени файла должна браться из одного места, у меня это `VERSION` в `Makefile`.

## Профилирование

Интуиция врёт: кажется, тормозит «сложная» функция, а время уходит на простой цикл. Без
профиля оптимизация — угадывание.

| Инструмент | Что показывает | Права |
|---|---|---|
| `time ./prog` | общее время, без деталей | не нужны |
| `gprof` | какие функции и сколько раз, доля времени | не нужны |
| `perf` | такты, промахи кеша, ветвления, стек | нужны (`perf_event_paranoid`) |

### gprof

```bash
gcc -O0 -pg -o hot hot.c     # -pg вставляет счётчики вызовов
./hot 34                     # при выходе пишет gmon.out в текущий каталог
gprof -b ./hot gmon.out | head -12
```

Без `-pg` файла `gmon.out` не будет. В плоском профиле `self` — время в самой функции,
`calls` — сколько раз вызвали. Рекурсия в `calls` не считается: у `fib` там 1, а в графе
вызовов `1+18454928`.

Время gprof меряет по таймеру с шагом 10 мс, поэтому проценты плавают от запуска к запуску.
Смотреть на порядок величин. Слишком быстрая программа даёт `no time accumulated`, надо
увеличить нагрузку.

На `-O2` профиль показывает уже другой код. Маленькие `static` функции встраиваются и
пропадают из списка, их время приписывается вызывающей. В `hot.c` с `-O2` `sum_squares` нет
вообще, gcc сам вынес её из цикла. Чтобы видеть функции отдельно, можно добавить
`-fno-inline`.

### Что делать с профилем

Порядок: алгоритм → структуры данных → флаги компилятора → микрооптимизации. Убрать лишние
вызовы (200 000 раз одно и то же — посчитать один раз), заменить квадратичный алгоритм на
линейный. После каждого шага снова `time` и `gprof`, без замера оптимизация — это вера.
Сравнивать только сборки с одинаковыми флагами.

> **Грабли:** иногда флаг даёт больше, чем ручная правка. На `hot.c` у меня `-O2` ускорил в 7.5 раз, а
> ручное удаление цикла поверх `-O2` уже ничего не добавило: компилятор сделал то же сам.
> Но квадратичный алгоритм он в линейный не превратит. В ДЗ замена O(n²) на O(n) дала
> 1 с → 0.001 с, и никакой флаг так не может.

## Чек-лист

- Артефакты не в Git, секреты никогда.
- `make clean && make` на чистой машине; особая настройка живёт в `Makefile`.
- Тест возвращает не 0 при ошибке.
- `ci.sh` и `ci.yml` делают одно и то же.
- Версия в одном месте.
- Сначала `time`, потом `gprof`, оптимизируется горячее.
