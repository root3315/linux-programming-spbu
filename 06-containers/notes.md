# Образы корневых файловых систем

## Контейнер и виртуалка

Программа зависит не только от кода: версия glibc и других библиотек, компилятор и make,
переменные окружения и локаль, конфиги и сертификаты, пользователь, от которого она
работает. Образ фиксирует всё это вместе с программой, и запуск сводится к «возьми образ и
запусти». Из одного образа можно поднять сколько угодно контейнеров, как из одного бинарника
сколько угодно процессов.

| | ВМ | Контейнер |
|---|---|---|
| Ядро | своё | общее с хостом |
| Запуск | секунды–минуты | доли секунды |
| Размер | гигабайты | мегабайты |
| Изоляция | полная | на уровне процессов |
| ОС | любая | только ядро хоста |

Контейнер — обычный процесс хоста, которому ядро ограничило видимость и ресурсы. Отсюда
следствие: Linux-контейнер на Windows или macOS «как есть» не запустится, Docker Desktop
поднимает для него скрытую виртуалку с Linux. У меня Docker Desktop на Windows, и это
видно прямо из контейнера:

```text
$ docker run --rm ubuntu:24.04 uname -r
6.18.58.1-microsoft-standard-WSL2
$ docker run --rm alpine:3.20 uname -r
6.18.58.1-microsoft-standard-WSL2
```

Ubuntu и Alpine, а ядро одно и то же: ядро виртуалки WSL2.

## Что делает ядро для контейнера

Три механизма, все знакомы по прошлым лекциям:

- namespaces — что процесс видит: свои PID, сеть, точки монтирования, имя узла;
- cgroups — сколько ему можно: CPU, память, ввод-вывод, число процессов;
- overlayfs — из чего собран его `/`: слои образа плюс записываемый слой сверху.

Namespaces видно в `/proc/<pid>/ns`: у процесса в контейнере свои `pid`, `net`, `mnt`, `uts`,
`ipc`, `cgroup`. Лимиты cgroups задаются флагами `docker run` и читаются изнутри:

```text
$ docker run --rm --memory 64m --pids-limit 50 alpine:3.20 \
    sh -c 'cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/pids.max'
67108864
50
```

Без флагов там `max`, ограничений нет.

## Образ — это слои

Образ состоит из слоёв только для чтения, каждая инструкция Dockerfile даёт слой (у
`CMD`, `USER`, `ENV` он нулевого размера). При запуске сверху кладётся записываемый слой,
свой у каждого контейнера. С `--rm` он исчезает вместе с контейнером.

Что это даёт: кэш при сборке, общие слои на диске хранятся один раз, при скачивании тянутся
только недостающие.

> **Грабли:** слой неизменяем. Если в одной инструкции поставить пакеты, а в следующей
> удалить их, образ не уменьшится: файлы остались в предыдущем слое. Чистить
> (`rm -rf /var/lib/apt/lists/*`) надо в том же `RUN`, где ставили.

`docker history <образ>` показывает слои сверху вниз, верхний — последний. Самый большой
слой почти всегда база или установка пакетов.

В Docker 29 `docker images` показывает две колонки: `DISK USAGE` (распакованные слои плюс
сжатые) и `CONTENT SIZE` (сжатое, сколько качать из реестра). Цифры со слайдов — это
`DISK USAGE`, например `alpine:3.20` занимает 12.2MB.

## Dockerfile

| Инструкция | Что делает |
|---|---|
| `FROM` | базовый образ, начало этапа |
| `RUN` | команда при сборке |
| `COPY` | файлы из контекста в образ |
| `WORKDIR` | рабочий каталог для следующих инструкций |
| `ENV` | переменная окружения |
| `USER` | от какого пользователя работать |
| `CMD` | аргументы/команда по умолчанию |
| `ENTRYPOINT` | сама программа |
| `EXPOSE` | документирует порт, но не публикует его |

### CMD и ENTRYPOINT

`ENTRYPOINT` — программа, `CMD` — аргументы по умолчанию. Аргумент в `docker run` заменяет
`CMD` целиком:

| В образе | `docker run img c` | `docker run img` |
|---|---|---|
| `CMD ["a","b"]` | запустится `c` | `a b` |
| `ENTRYPOINT ["a"]` + `CMD ["b"]` | `a c` | `a b` |

Поэтому в образе на `scratch` с `ENTRYPOINT ["/hello"]` команда `docker run img sh` не
ругается, а печатает `Hello, sh!`: `sh` стал аргументом. Чтобы правда запустить оболочку,
нужен `--entrypoint sh`, и тогда `exec: "sh": executable file not found in $PATH`.

Две формы записи: exec-форма `CMD ["/app/hello", "world"]` запускает программу напрямую,
shell-форма `CMD /app/hello world` запускает её через `/bin/sh -c`. Для сервисов только
exec-форма, причина ниже в разделе про PID 1.

### Кэш и порядок инструкций

Docker сравнивает инструкцию и содержимое файлов, которые она трогает, со своим кэшем.
Совпало — слой берётся готовым. Изменилось — пересобирается этот слой и все ниже. Проверил
на наивном образе: дописал строку в `app/data.txt`, и `apt-get install` остался `CACHED`,
пересобрались только `COPY app/ .` и `RUN make`. Вся сборка 2 секунды вместо полутора минут.

> **Запомнить:** редко меняющееся (установка пакетов) пишем выше, часто меняющееся
> (исходники) ниже. Иначе каждая правка кода тянет переустановку компилятора.

### Контекст и .dockerignore

Контекст сборки — всё, что лежит в каталоге из конца `docker build ... .`. Его целиком
отправляют демону. В `.dockerignore` пишут то, что образу не нужно: `.git`, объектники,
сами Dockerfile, README, локальные секреты. Файл, не попавший в контекст, не может случайно
попасть в образ через `COPY`.

Шаблон `.env` в `.dockerignore` закрывает только файл в корне контекста. `app/.env` с ним
спокойно доезжает до образа, нужен `**/.env`. Проверил в ДЗ.

## Хороший образ

### Multistage

Два `FROM` в одном файле. Первый этап (`AS builder`) — «цех»: компилятор, заголовки,
исходники. Второй — «витрина»: туда копируется только бинарник через
`COPY --from=builder`. Второй этап не наследует первый, в нём только то, что скопировано явно.

На примере из Chapter 06: этап builder на alpine с `build-base` весит 318MB, финальный образ
12.2MB, из них бинарник 28.7kB. Наивный вариант с gcc внутри у меня вышел 406MB.

### scratch и статическая сборка

`scratch` — пустой образ: ни оболочки, ни libc, ни `/etc/passwd`. Туда кладут
статически собранный бинарник (`gcc -static`), образ получается в сотни килобайт.

> **Грабли:** динамический бинарник в `scratch` не запускается с ошибкой
> `exec /hello: no such file or directory`. Файл на месте, нет загрузчика (`ld-musl` или
> `ld-linux`), который указан в ELF. Поэтому для `scratch` только `-static`.

Выбор базы: alpine, когда нужна оболочка и пакеты (отладка, скрипты); scratch, когда хватает
одного статического бинарника. Зайти внутрь `scratch` и «посмотреть» нельзя, это и
ограничение, и защита.

### Безопасность

- `USER 65534:65534` (nobody) или свой пользователь: взлом процесса даёт минимум прав.
- Фиксированный тег: `alpine:3.20`, а не `alpine:latest`, который однажды соберётся иначе.
- Секреты не кладём в слои: `ENV PASSWORD=...` и `COPY .env` остаются в истории образа
  навсегда, даже если следующий слой их удалит. Для сборки есть `--secret`, для запуска
  переменные окружения.
- Перед публикацией: `docker history` (нет ли ключей в командах), сканер уязвимостей
  (`docker scout cves`, `trivy`), проверка `.dockerignore`.

## PID 1 и сигналы

Внутри контейнера PID 1 — это команда из `CMD`/`ENTRYPOINT`, а не systemd:

```text
$ docker run -d --name demo alpine:3.20 sleep 300
$ docker exec demo ps aux
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 300
    7 root      0:00 ps aux
```

`docker stop` шлёт SIGTERM процессу PID 1, ждёт таймаут (по умолчанию 10 с) и добивает
SIGKILL. Ядро не применяет к PID 1 действие по умолчанию для сигналов, на которые нет
обработчика. Поэтому `sleep` как PID 1 SIGTERM просто не замечает:

| Что было PID 1 | `docker stop -t 10` | Код выхода |
|---|---|---|
| `sleep 300` | 10.5 с | 137 (SIGKILL) |
| `sleep 300` с `--init` | 0.3 с | 143 (SIGTERM) |
| моя программа с `sigaction(SIGTERM)` | 0.4 с | 0 |
| `sh -c 'моя программа; echo'` | 10.4 с | 137 |

Последняя строка — та самая проблема shell-формы: PID 1 становится `sh`, сигнал уходит ему,
а программа его не видит. Три способа не попасться: exec-форма `CMD`, свой обработчик
SIGTERM, флаг `--init` (Docker ставит `/sbin/docker-init` PID 1, тот пересылает сигналы и
собирает зомби).

> **Грабли:** в моём Docker Desktop у новых контейнеров `StopTimeout` оказался 1 с (видно в
> `docker inspect`), и первый `docker stop` вышел за 1.5 с с кодом 137. Для честного замера
> таймаут пишу явно: `docker stop -t 10`.

Ещё одна мелочь из ДЗ: в контейнере stdout — не терминал, вывод буферизуется блоками, и
`docker logs` у работающего сервиса показывает не всё. Лечится `setvbuf(stdout, NULL,
_IOLBF, 0)` в начале `main`.

## Данные

Записываемый слой живёт, пока жив контейнер. Всё состояние держим снаружи:

| Запись | Где данные |
|---|---|
| `-v data:/app/data` | том Docker, переживает контейнер |
| `-v "$PWD/out:/app/out"` | каталог хоста, видно сразу |
| `--tmpfs /tmp` | память, исчезает с контейнером |

```text
$ docker run --rm -v demo-data:/data alpine:3.20 sh -c 'echo hi > /data/f'
$ docker run --rm -v demo-data:/data alpine:3.20 cat /data/f
hi
$ docker run --rm alpine:3.20 sh -c 'echo hi > /tmp/f'
$ docker run --rm alpine:3.20 cat /tmp/f
cat: can't open '/tmp/f': No such file or directory
```

Монтирование каталога хоста даёт программе доступ к файлам с правами пользователя из
контейнера, поэтому монтируем только нужное. Пустой именованный том при подключении берёт
владельца у каталога в образе: если в образе нет `/data`, принадлежащего `nobody`, то
процесс под `USER 65534` писать в том не сможет.

## compose

`compose.yml` описывает набор сервисов. `docker compose up` собирает образы, создаёт сеть
(сервисы видят друг друга по имени) и запускает всё, `docker compose down` удаляет
контейнеры и сеть. Образы и тома остаются, тома удаляет `down -v`. `stop` только
останавливает контейнеры, их можно поднять снова.

| Команда | Что делает |
|---|---|
| `docker compose config` | показывает, как compose понял файл |
| `docker compose up -d` | запуск в фоне |
| `docker compose ps -a` | статус, включая завершённые |
| `docker compose logs <сервис>` | вывод одного сервиса |
| `docker compose down [-v]` | удалить контейнеры и сеть [и тома] |

Если в двух сервисах написано `build: .`, compose собирает два образа (`<проект>-hello-ru`
и `<проект>-hello-en`) с одинаковыми слоями, но разными ID. Чтобы образ был один, у первого
сервиса `build` + `image: имя`, у второго только `image: имя`.

Контейнер живёт, пока живёт PID 1. Программа из Chapter 06 печатает приветствие и
завершается, поэтому в `docker compose ps -a` оба сервиса `Exited (0)`, это нормально.

## Чек-лист образа

1. Multistage и лёгкая база, вес проверен `docker images` и `docker history`.
2. Зависимости выше, исходники ниже.
3. `CMD`/`ENTRYPOINT` в exec-форме.
4. `USER`, фиксированный тег, секретов нет в слоях, есть `.dockerignore`.
5. Состояние в томе, а не в записываемом слое.
6. Образ запущен, а не только собран: `docker run --rm`, `docker compose up`.
