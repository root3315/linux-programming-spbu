# Отчёт по ДЗ 9: чат на двоих

Проверял в контейнере с Ubuntu 24.04 (gcc 13.3, iproute2, netcat-openbsd). Сервер слушает только
`127.0.0.1`, строка принимается до 512 байт, имя до 32 байт.

## 1. Как запустить сервер и клиент

Сборка (флаги `-std=c11 -Wall -Wextra -Werror`, предупреждений нет):

```text
$ make
cc -std=c11 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Werror -O2 -o chat_server chat_server.c
cc -std=c11 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Werror -O2 -o chat_client chat_client.c
```

Терминал 1, сервер:

```text
$ ./chat_server 9100
слушаю 127.0.0.1:9100 (Ctrl+C — выход)
```

Терминал 2, клиент. Формат `./chat_client HOST PORT ИМЯ [сообщение ...]`, несколько сообщений
уходят подряд по одному соединению:

```text
$ ./chat_client 127.0.0.1 9100 Степан "привет" "как дела" "третье"
привет, Степан! ты сказал: привет
привет, Степан! ты сказал: как дела
привет, Степан! ты сказал: третье
```

Если сообщений в аргументах нет, клиент читает строки из stdin:

```text
$ printf 'я второй клиент\nи ещё строка\n' | ./chat_client 127.0.0.1 9100 Аня
привет, Аня! ты сказал: я второй клиент
привет, Аня! ты сказал: и ещё строка
```

Что при этом печатает сервер (счётчик сквозной, по всем клиентам):

```text
клиент 127.0.0.1:43000 подключился
[1] Степан: привет
[2] Степан: как дела
[3] Степан: третье
клиент ушёл, всего сообщений: 3
клиент 127.0.0.1:51964 подключился
[4] Аня: я второй клиент
[5] Аня: и ещё строка
клиент ушёл, всего сообщений: 5
```

Плохие строки сервер отклоняет, не падает и не рвёт соединение. Проверял сырыми строками через
`nc -N`, потому что мой клиент сам добавляет `имя: `:

```text
$ printf 'без двоеточия\n' | nc -N 127.0.0.1 9100
ошибка: нет двоеточия, нужен формат «имя: сообщение»
$ printf '\n' | nc -N 127.0.0.1 9100
ошибка: пустая строка, нужен формат «имя: сообщение»
$ printf 'Вася:\n' | nc -N 127.0.0.1 9100
ошибка: пустое сообщение
$ (printf 'Вася: '; head -c 100000 /dev/zero | tr '\0' a; echo) | nc -N 127.0.0.1 9100
ошибка: строка длиннее 512 байт
$ printf 'Вася: ещё жив\n' | nc -N 127.0.0.1 9100
привет, Вася! ты сказал: ещё жив
```

Строка в 100000 байт читается до конца и выбрасывается, следующая обрабатывается нормально.
Граница проверена: имя и сообщение вместе 510 байт проходят, 516 байт получают отказ.

## 2. Вывод ss во время работы

Сервер ждёт подключений:

```text
$ ss -ltnp 'sport = :9100'
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      5          127.0.0.1:9100      0.0.0.0:*    users:(("chat_server",pid=26,fd=3))
```

Пока один клиент держит соединение, а второй уже подключился и ждёт очереди:

```text
$ ss -tnp 'sport = :9100 or dport = :9100'
State Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
ESTAB 0      0          127.0.0.1:42780    127.0.0.1:9100  users:(("nc",pid=30,fd=3))
ESTAB 0      0          127.0.0.1:42788    127.0.0.1:9100  users:(("chat_client",pid=34,fd=3))
ESTAB 0      0          127.0.0.1:9100     127.0.0.1:42780 users:(("chat_server",pid=26,fd=4))
ESTAB 58     0          127.0.0.1:9100     127.0.0.1:42788
```

Читаю так: порт 9100 слушает `chat_server`, сокет на дескрипторе 3. Принятое соединение первого
клиента на дескрипторе 4. Строка без процесса с `Recv-Q 58` — это соединение второго клиента: ядро его
уже приняло, 58 байт сообщения лежат в буфере, `accept` до него ещё не дошёл.
Поэтому и у слушающего сокета `Recv-Q` в этот момент 1: одно соединение ждёт в очереди.

## 3. Что будет при неверном порте

| Что запустил | Что получил | Код выхода |
| --- | --- | --- |
| `./chat_client 127.0.0.1 abc Я hi` | неверный порт: abc (нужно число от 1 до 65535) | 2 |
| `./chat_client 127.0.0.1 0 Я hi` | то же, про порт 0 | 2 |
| `./chat_client 127.0.0.1 70000 Я hi` | то же, про порт 70000 | 2 |
| `./chat_client 127.0.0.1 80x Я hi` | то же, про 80x | 2 |
| `./chat_server 70000` | неверный порт: 70000 (нужно число от 1 до 65535) | 2 |
| `./chat_server` | использование: ./chat_server PORT | 2 |
| `./chat_client localhost 9100 Я hi` (имя вместо адреса) | плохой адрес: localhost | 2 |
| `./chat_client 127.0.0.1 9999 Я hi` (там никто не слушает) | connect: Connection refused | 1 |
| `./chat_server 9100` (порт уже занят) | bind: Address already in use | 1 |

Первые пять строк отсеивает `parse_port` до любых сетевых вызовов: `strtol`, проверка, что
после числа ничего нет, и диапазон 1–65535. Шестую даёт проверка числа аргументов. Последние две ошибки приходят от системы: порт
правильный, но с ним что-то не так. Это разные вещи, и код выхода у них другой. Седьмая строка не
про порт: `inet_pton` не разбирает имена, только цифры.

## 4. Что было непонятно

- Второй клиент во время разговора первого не получает ошибку, а просто молчит. Сервер
  последовательный, поэтому второй ждёт в очереди `listen`, и `connect` у него уже успешен. Это видно
  в `ss`: `ESTAB` и ненулевой `Recv-Q` на стороне сервера. Сначала думал, что завис клиент.
- Клиент принимает только IP. `./chat_client localhost 9100 Я hi` отвечает «плохой адрес: localhost»,
  а не «Name or service not known», как в таблице у преподавателя: `inet_pton` имена не разбирает, для
  этого нужен `getaddrinfo`. Оставил как есть, в задаче адрес всегда `127.0.0.1`.
- Строка без перевода строки на конце не обрабатывается. При первом тесте длинной строки я
  сделал её через `head -c | tr | sed`, `\n` в конце не оказалось, и сервер молча ничего не
  ответил: ждал конца строки, а потом клиент ушёл. Пришлось добавить `echo` в команду. Так
  и оставил, протокол построчный.
