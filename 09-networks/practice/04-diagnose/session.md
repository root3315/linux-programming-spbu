# Практика 4. Найти поломку

Поломку никто не готовил, поэтому устроил их сам, по списку со слайда. Для каждой записал, какая
команда показала причину. Использую `echo_server`, `echo_client`, `http_get` и `diag.sh` из
архива Chapter 09 без правок. Из практики 3 всё ещё работает `python3 -m http.server 8001`.

## Осмотр целиком: diag.sh

```text
stepan@box:~/net-lab$ sh ./diag.sh 127.0.0.1 8080
1. Мои адреса
   lo               UNKNOWN        127.0.0.1/8 ::1/128
   eth0@if37        UP             172.17.0.4/16

2. Куда уходит трафик по умолчанию
   default via 172.17.0.1 dev eth0
   172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.4

3. Кто слушает порты на этой машине
   State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
   LISTEN 0      5            0.0.0.0:8001      0.0.0.0:*

4. Пускают ли на 127.0.0.1:8080
   закрыто или никто не слушает

5. Что ответит HTTP, если это веб-сервер
   HTTP не ответил
```

Адреса и маршрут нормальные, на 8080 никто не слушает. Заодно виден `0.0.0.0:8001`: этот
`http.server` я запустил без `--bind`, и он доступен всей сети, не только мне.

## 1. Сервер не запущен

```text
stepan@box:~/net-lab$ ./echo_client 127.0.0.1 8080 тест
connect: Connection refused
stepan@box:~/net-lab$ ss -ltn | grep 8080
stepan@box:~/net-lab$ echo $?
1
stepan@box:~/net-lab$ nc -z 127.0.0.1 8080; echo $?
1
```

Хватило первой строки: `Connection refused` значит «машина ответила, порт закрыт». `ss` пустой, у
`nc -z` код 1. Лечение: запустить сервер.

## 2. Сервер слушает другой порт

Запустил `./echo_server 8090 &`, а клиент идёт на 8080:

```text
stepan@box:~/net-lab$ ss -ltn | grep 80
LISTEN 0      5            0.0.0.0:8001      0.0.0.0:*
LISTEN 0      5          127.0.0.1:8090      0.0.0.0:*
stepan@box:~/net-lab$ nc -z 127.0.0.1 8080; echo "8080 -> $?"
8080 -> 1
stepan@box:~/net-lab$ nc -z 127.0.0.1 8090; echo "8090 -> $?"
Connection to 127.0.0.1 8090 port [tcp/*] succeeded!
8090 -> 0
```

Ошибка у клиента та же, `Connection refused`, поэтому её текст не отличает «не запущен» от «не
тот порт». Отличает `ss -ltn`: в списке есть 8090, а 8080 нет.

## 3. Порт занят старым процессом

```text
stepan@box:~/net-lab$ ./echo_server 8090
bind: Address already in use
```

Сервер сам назвал причину, до сети дело не дошло. Кто занял, показывает `ss -ltnp | grep 8090`.

## 4. Имя вместо адреса и чужой адрес

```text
stepan@box:~/net-lab$ ./echo_client localhost 8090 x
плохой адрес: localhost
stepan@box:~/net-lab$ timeout 8 ./echo_client 10.255.255.1 8090 x; echo rc=$?
rc=124
stepan@box:~/net-lab$ nc -z -w 2 10.255.255.1 8090; echo rc=$?
rc=1
```

Клиент из архива принимает только цифры (`inet_pton`), поэтому «Name or service not known» из
README преподавателя я не получил, а получил «плохой адрес». На адрес, которого в сети нет,
клиент ничего не пишет и ждёт: через 8 секунд его убил `timeout` (код 124). Это тот самый
«Timeout»: компьютер не ответил вообще, в отличие от `Connection refused`. `nc -z -w 2` сдаётся
за 2 секунды, с ним удобнее.

## 5. На порту не тот сервер

Эхо-сервер на 8090, а я иду к нему как к веб-серверу:

```text
stepan@box:~/net-lab$ curl -i --max-time 3 http://127.0.0.1:8090/
curl: (1) Received HTTP/0.9 when not allowed
stepan@box:~/net-lab$ timeout 3 ./http_get 127.0.0.1 8090 /; echo "rc=$?"
rc=124
```

Строки индикатора загрузки curl здесь убраны, они идут в stderr. curl получил своё же `GET / HTTP/1.1`
обратно и сказал, что это не HTTP-ответ. `http_get` повис, и это интереснее. `echo_server` читает,
пока клиент не закроет свою сторону (`read` вернёт 0), а `http_get` после запроса ничего не
закрывает и ждёт конца ответа. Оба ждут друг друга. Эхо-клиент в архиве делает
`shutdown(sock, SHUT_WR)` как раз из-за этого. Здесь вмешался `timeout` через 3 секунды.

## Порядок проверок

1. Прочитать текст ошибки. `Connection refused`: адрес верный, порт закрыт. `bind: Address already
   in use`: порт занят. «плохой адрес»: клиент не понял, что ему дали.
2. `ss -ltn | grep ПОРТ`: слушает ли кто-то нужный порт и на каком адресе (`127.0.0.1` или `0.0.0.0`).
3. `nc -z -w 2 ХОСТ ПОРТ`: пускают ли с моей стороны. Не зависает, в отличие от клиента.
4. `curl -i` или `strace -e trace=connect,read,write`: что на самом деле говорит приложение.

## Что понял

Большую часть случаев разбирает текст ошибки плюс `ss -ltn`. `Connection refused` и таймаут говорят
о разном: отказ приходит сразу и значит «я здесь, но порт закрыт», тишина значит «до адреса не
дойти». `ip addr` и `ip route` из первых двух проверок на петле ничего не покажут, они нужны,
когда сервер на другой машине.
