# Как устроен репозиторий

Здесь записаны правила, по которым я веду репозиторий. Они нужны мне самому, чтобы через
месяц не гадать, где что лежит, и тем, кто захочет что-то поправить.

## Папка занятия

Каждое занятие лежит в папке `NN-название` (латиницей), например `04-build-toolchain`.
Внутри обычно так:

```text
04-build-toolchain/
├── README.md          что было на занятии и где что лежит
├── notes.md           конспект лекции
├── notes.pdf          тот же конспект в PDF
├── practice/
│   ├── README.md      условия практик
│   └── 01-stages/     решение: файлы и session.md с командами и выводом
└── homework/
    ├── README.md      условие и критерии
    ├── REPORT.md      отчёт
    └── build-homework.tar.gz   архив для сдачи
```

Если на занятии не было практики или домашнего задания, папки `practice/` или `homework/`
просто нет.

Слайды лекций и архивы с примерами преподавателя я сюда не кладу, это не мои материалы.
Если решение опирается на пример из архива, в `README.md` написано, откуда его скачать.

## Ветки

Каждая задача начинается с issue. Ветка создаётся от свежего `main` и называется
`тип/номер-issue-кратко`:

```text
feat/12-lec05-processes
docs/1-contributing
fix/20-lec04-report
```

В `main` напрямую не коммичу.

## Коммиты

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): тип и область
на английском, описание по-русски, со строчной буквы, без точки в конце, не длиннее 72
символов.

```text
docs(lec04): конспект лекции о сборке программ
feat(lec04/practice): разобрать этапы сборки на stages/demo.c
feat(lec04/hw): добавить модуль stats
build(lec04): собрать notes.pdf
```

| Тип | Когда |
|---|---|
| `docs` | конспекты, условия, отчёты, README |
| `feat` | решение практики или домашнего задания |
| `fix` | исправление ошибки в решении или тексте |
| `build` | сборка PDF, Makefile, архивы для сдачи |
| `ci` | GitHub Actions |
| `test` | тесты |
| `perf` | ускорение |
| `refactor` | переделка без изменения поведения |
| `chore` | всё служебное |

Область: `repo`, `tools`, `lec01`…`lec10`, `lec04.5`, а для частей занятия `lec05/practice`
и `lec05/hw`.

Один коммит — одно изменение. Конспект, условия, каждая практика и домашка идут
отдельными коммитами.

## Pull request

Заголовок PR: `Занятие 5: процессы и сигналы`. В описании три части: что сделано, как
проверено, что осталось и какие есть вопросы. В конце `Closes #N`.

Перед слиянием я ещё раз читаю весь diff. Сливаю обычным merge, без squash, чтобы в
истории остались отдельные шаги. Ветку после слияния удаляю.

## Код и проверка

Всё запускаю в Ubuntu 24.04 (GCC 13, GNU Make 4.3, CMake 3.28), как на занятиях. На Windows
это контейнер, инструменты в нём ставлю сразу после запуска:

```bash
docker run --rm -it -v "${PWD}:/work" -w /work ubuntu:24.04 bash
apt update && apt install -y build-essential gdb cmake git
```

Команда работает в PowerShell и в Linux. В Git Bash перед ней нужно `MSYS_NO_PATHCONV=1`,
иначе путь `/work` превратится в виндовый.

- Код собирается с `-Wall -Wextra` без предупреждений.
- Вывод команд в отчётах настоящий, из контейнера. Длинный вывод сокращаю строкой `...`.
- Объектные файлы и `build/` отсекает `.gitignore`. Бинарники без расширения он не видит,
  поэтому перед коммитом смотрю `git status` или делаю `make clean`.

## Текст

- Пишу коротко и по делу, как конспект для себя.
- Код в блоках с указанием языка: `bash`, `c`, `make`, `text` для вывода.
- Ссылки между файлами относительные.
- Конспект пишу в `notes.md`, PDF собираю из него и руками не правлю. Как собрать, написано
  в [tools/notes](tools/notes/README.md).
