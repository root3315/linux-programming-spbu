# Сборка программ в Linux

Лекция-практикум: четыре этапа сборки руками, потом Make, CMake (немного Meson и autotools),
потом проверка кода. Правило занятия: сначала предсказать команду и её вывод, потом
запустить, потом сверить. Сообщение об ошибке почти всегда содержит файл, строку и
причину, его надо читать сверху вниз: первая ошибка обычно главная.

## Четыре этапа

`gcc` — это драйвер: одна команда по очереди запускает препроцессор, компилятор, ассемблер и
линковщик. Каждый этап можно остановить флагом:

| Команда | Этап | Что получаем |
|---|---|---|
| `gcc -E demo.c > demo.i` | препроцессор (cpp) | текст C с раскрытыми `#include` и `#define` |
| `gcc -S demo.c` | компилятор (cc1) | `demo.s`, ассемблер |
| `gcc -c demo.c` | ассемблер (as) | `demo.o`, объектный файл |
| `gcc demo.o -o demo` | линковщик (ld) | `demo`, исполняемый файл |

Запускать можно только результат последнего шага. В `.o` нет стартового кода, чужих функций
и расставленных адресов.

### Препроцессор

Работает с текстом и ничего не знает о типах. `#include` вставляет файл целиком, `#define`
подставляет текст, `#if/#ifdef` выкидывают блоки, include guard (`#ifndef GREET_H`) или
`#pragma once` защищают от двойного включения. Из 21 строки `demo.c` получилось 834 строки
`demo.i`, почти всё из `stdio.h`.

Макрос — это подстановка текста, а не функция:

```c
#define BAD_SQUARE(x) x * x
#define SQUARE(x) ((x) * (x))
printf("%d %d\n", BAD_SQUARE(1 + 2), SQUARE(1 + 2));
```

```text
$ gcc -E macro.c | tail -4
{
    printf("%d %d\n", 1 + 2 * 1 + 2, ((1 + 2) * (1 + 2)));
    return 0;
}
$ ./macro
5 9
```

> **Грабли:** скобки в макросе обязательны и вокруг каждого параметра, и вокруг всего тела.
> И никаких `a++` в аргументах: аргумент вычислится столько раз, сколько раз имя параметра
> встречается в теле. Константы лучше делать через `const` или `enum`.

### Компилятор: флаги

Рабочий минимум со слайда: `gcc -std=c11 -Wall -Wextra -O2 -g main.c greet.c -o hello`.

- `-Wall -Wextra` включают почти все полезные предупреждения. Ещё есть `-Wpedantic`,
  `-Wshadow`, `-Wconversion`.
- `-Werror` превращает предупреждения в ошибки. Хорошо для CI, но новый компилятор может
  добавить предупреждение и «сломать» старый код, поэтому в CI фиксируют версию gcc.
- `-O0`…`-O3` уровень оптимизации, `-std=c11` стандарт языка.
- `-g` не замедляет программу, а добавляет отладочную информацию. Без неё gdb не покажет
  имена переменных и строки.
- `-I` каталог заголовков, `-L` каталог библиотек, `-l` сама библиотека.

### Объектный файл

`.o` — это ELF с машинным кодом и таблицей символов. Секции: `.text` код, `.rodata` строки и
константы, `.data` инициализированные переменные, `.bss` переменные с нулём (место в файле
не занимают). Смотреть через `nm` и `size`:

```text
$ nm demo.o
0000000000000000 d app_name
0000000000000000 B global_counter
0000000000000000 T main
                 U printf
```

`T` определён в коде, `B` глобальная в `.bss`, `d` локальная (`static`) в данных, `U`
нужен снаружи, его должен найти линковщик. Заглавная буква значит глобальный символ,
строчная локальный.

### Линковщик

Собирает `.o` и библиотеки, сопоставляет имена: каждому `U` ищет определение, размещает
секции, добавляет точку входа `_start`. Динамическая линковка (по умолчанию) оставляет
`libc.so.6` снаружи, её подгрузит `ld-linux-x86-64.so.2` при запуске, это видно в `ldd`.
Статическая (`-static`) вклеивает всё внутрь: у меня `demo` был 16 КБ, а `demo-static`
785 КБ, зато не зависит от библиотек системы.

> **Запомнить:** «компилятор не видит функцию» почти всегда неправда. Если ошибка
> `undefined reference`, а в конце `ld returned 1 exit status`, то компиляция прошла, а
> линковщику не дали файл с определением.

## Типичные ошибки сборки

| Сообщение | Этап | Причина | Лечение |
|---|---|---|---|
| `undefined reference to 'greet'` | линковка | функция объявлена, но её `.c` не передан | добавить `greet.c` или библиотеку |
| `multiple definition of 'helper'` | линковка | одна функция определена в двух `.c` | одно определение, в `.h` только прототип, или `static` |
| `implicit declaration of function 'strlen'` | компиляция | забыт `#include <string.h>` | добавить заголовок |
| `missing separator` | make | в рецепте пробелы вместо табуляции | табуляция, проверка через `cat -A` |

В gcc 13 `implicit declaration` пока предупреждение, и программа собирается. С `-Werror`
сборка останавливается.

## Make

Make решает одну задачу: по графу зависимостей понять, что пересобрать, и запустить только
нужные команды. Решение принимается по времени изменения файлов, а не по содержимому:
если зависимость новее цели, цель пересобирается. Поэтому `touch файл` делает файл «новым».

Правило состоит из цели, зависимостей и рецепта. Рецепт начинается с табуляции:

```make
CC      = gcc
CFLAGS  = -std=c11 -Wall -Wextra -O2 -g
TARGET  = hello
OBJS    = main.o greet.o

.PHONY: all clean run

all: $(TARGET)

$(TARGET): $(OBJS)
	$(CC) -o $@ $^

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

main.o: greet.h
greet.o: greet.h
```

Автоматические переменные: `$@` имя цели, `$<` первая зависимость, `$^` все зависимости.
Строки `main.o: greet.h` нужны, чтобы правка заголовка пересобирала всех, кто его включает.
`touch greet.h` пересобирает оба объекта и перелинковывает `hello`.

`.PHONY` нужен для целей, которые не создают файл (`all`, `clean`, `run`). Без него файл
с таким же именем в каталоге убедит make, что цель уже собрана. Проверил: `touch run` и
без `.PHONY` получаю `make: 'run' is up to date.`

| Команда | Что делает |
|---|---|
| `make` | первая цель в файле, обычно `all` |
| `make hello` | конкретная цель |
| `make -n` | показать команды, ничего не выполняя |
| `make -j4` | собирать в 4 потока |
| `make -B` | пересобрать всё |
| `make -f Other.mk` | другой файл правил |

> **Грабли:** табуляция в рецепте. Редактор может молча подставить пробелы. Make 4.3 тогда
> пишет `missing separator (did you mean TAB instead of 8 spaces?)`. В `cat -A` табуляция
> видна как `^I`, а в vim помогает `:set list`.

Make не знает о смене флагов. Если пересобрать с другим `CFLAGS`, старые `.o` останутся
«свежими». Поэтому release-сборку делают через `clean` или в отдельный файл.

## CMake

CMake не собирает сам, а генерирует систему сборки (Makefile, Ninja) под текущую платформу
и компилятор. Описываются цели и их свойства, а не команды.

```cmake
cmake_minimum_required(VERSION 3.16)
project(hello C)
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
add_library(greet STATIC greet.c)
target_include_directories(greet PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
target_compile_options(greet PRIVATE -Wall -Wextra)
add_executable(hello main.c)
target_link_libraries(hello PRIVATE greet)
```

`PUBLIC` передаёт свойство тем, кто линкуется с целью (так `hello` получает `-I` на
`greet.h`), `PRIVATE` оставляет только цели. Сборка всегда вне исходников:

```bash
cmake -S . -B build        # настроить: -S исходники, -B каталог сборки
cmake --build build        # собрать
cmake --build build --verbose   # увидеть реальные команды gcc
```

Зависимости от заголовков CMake отслеживает сам: передаёт gcc `-MD -MF файл.o.d`, gcc
записывает, какие заголовки включил. Руками ничего перечислять не надо. Отладочная и
релизная сборка живут рядом в разных каталогах (`build`, `build-release` с
`-DCMAKE_BUILD_TYPE=Release`).

> **Грабли:** `CMAKE_C_STANDARD 11` даёт `-std=gnu11`, а не `-std=c11`. Чтобы был чистый
> стандарт, нужен ещё `set(CMAKE_C_EXTENSIONS OFF)`. И без `CMAKE_BUILD_TYPE` нет ни `-O2`,
> ни `-g`.

## Meson и autotools

Meson: короткое описание, собирает ninja. Каталог сборки обязателен.

```meson
project('hello', 'c', version: '1.0.0',
  default_options: ['c_std=c11', 'warning_level=2'])
greet = static_library('greet', 'greet.c')
executable('hello', 'main.c', link_with: greet)
```

```bash
meson setup builddir && meson compile -C builddir
```

Встречается в GNOME, GStreamer, Mesa. Ставится через `apt install meson ninja-build`.

Autotools старше всех: сначала `./configure` проверяет систему и делает Makefile под неё,
потом обычный `make`. Пишутся два файла: `configure.ac` (что проверить) и `Makefile.am` (что
собрать), а `autoreconf --install` генерирует из них `configure`, `Makefile.in` и десяток
служебных файлов. Так собираются GCC, bash, coreutils.

| | Make | CMake | Meson | autotools |
|---|---|---|---|---|
| Что пишешь | правила и команды | цели и свойства | цели и значения | что проверить и что собрать |
| Запуск | `make` | `cmake -S . -B build` | `meson setup builddir` | `./configure` |
| Кто собирает | make | make или ninja | ninja | make |
| Проверка системы | нет | `find_package` | `dependency()` | `AC_CHECK_*` |

Выбирать стоит одну систему. Если держать в проекте сразу Makefile, CMakeLists.txt и
meson.build, они рано или поздно разойдутся.

## Проверка кода

### Санитайзеры

Ловят ошибки во время работы программы, которые без них выглядят как «иногда падает».

```bash
gcc -fsanitize=address,undefined -g -O1 memory.c -o memory
```

ASan (address) показывает выход за границы, use-after-free, утечки: точное место записи,
размер, границы блока и где он выделен. UBSan (undefined) ловит неопределённое поведение:
переполнение знакового целого, сдвиг на отрицательное число, деление на ноль, выход за
границы массива. Программа под ними в 2–3 раза медленнее и ест больше памяти, поэтому их
включают в тестах, а не в релизе.

> **Грабли:** UBSan по умолчанию только печатает `runtime error` и работает дальше, код
> выхода 0. Для CI нужен `-fno-sanitize-recover=all`, тогда программа завершается с
> ошибкой.

На `broken/memory.c` (цикл `i <= 4` по массиву из 4 `int`) обычная сборка печатает
`last=9` и выходит с кодом 0, а ASan сразу пишет `heap-buffer-overflow`,
`WRITE of size 4`, `memory.c:20`, `0 bytes after 16-byte region`.

### Статический анализ

Без запуска: `gcc -Wall -Wextra` на этапе компиляции, `cppcheck` (неинициализированные
переменные, утечки, мёртвый код), `clang-tidy` (стиль и ошибки API), `scan-build` (пути
выполнения, ведущие к ошибке). Команда со слайда: `cppcheck --enable=warning,style hello/`.
На `memory.c` cppcheck у меня ошибку не нашёл, санитайзер он не заменяет.

### gdb

Минимум: `break`, `run`, `next`, `print`, и `bt`, когда программа уже упала. Собирать с
`-g`, лучше с `-O0`. Удобно условие на точке останова:

```bash
gdb -q -batch -ex 'break memory.c:20 if i == 4' -ex run -ex 'print i' ./memory-dbg
```

## Чек-лист сборки

1. Понять, чем собирать: компилятор и версия, стандарт, исходники, библиотеки.
2. Включить `-Wall -Wextra`, в CI ещё `-Werror`.
3. Заголовки должны быть в зависимостях, иначе правка `.h` даст «старые» баги.
4. Проверять сборку с нуля: `make clean && make` или `rm -rf build`.
5. Отдельная сборка с `-fsanitize=address,undefined` и прогон тестов на ней.
6. Записать команду сборки в README, Makefile или CMakeLists.txt.

Минимум для сдачи: `make clean && make` без предупреждений, запуск с аргументом и без,
санитайзер молчит.
