# Как проверить программу

## Сюжет занятия

Есть функция `make_greeting(out, cap, name)`, она кладёт в буфер `"Hello, <name>!"`. К ней
восемь тестов, все зелёные. При этом в коде `strcpy` + `strcat` без проверки длины: длинное
имя пишется за край буфера. Тесты этого не видят, потому что длинного имени в них нет.
Дальше пять инструментов, и каждый находит что-то своё.

| Проверка | Вопрос | Чем | Слепое пятно |
|---|---|---|---|
| тесты | правильно ли считает | `make test`, свои `check()` | только то, что придумал человек |
| покрытие | всё ли проверили | `gcc --coverage`, `gcov` | строка выполнилась, но на удобных данных |
| санитайзер | не портит ли память | `-fsanitize=address,undefined` | только путь, который реально выполнился |
| фаззер | не падает ли на странном | случайные входы + проверки | не знает правильного ответа |
| линтер | нет ли глупостей в тексте | `cppcheck`, `clang-tidy` | не запускает код, бывают ложные срабатывания |

Ни один из них не доказывает, что ошибок нет. Зелёные тесты значат только «вот эти случаи
работают».

## Тесты

Тест — это вопрос, ответ на который известен заранее. Четыре шага: подготовить данные,
один раз вызвать функцию, сравнить с ожиданием, сообщить результат. В проекте это обёртка:

```c
static void check(int ok, const char *what)
{
    if (ok) {
        printf("ok:   %s\n", what);
    } else {
        printf("FAIL: %s\n", what);
        failed++;
    }
}
```

`failed++` вместо выхода, чтобы за один прогон увидеть все сломанные проверки. В конце
`main` при `failed != 0` возвращает 1, иначе 0. `make` смотрит на код возврата, а не на
слово FAIL.

```text
$ ./tests/test_greeting > /dev/null; echo "код теста: $?"
код теста: 1
$ make test; echo "код: $?"
...
make: *** [Makefile:28: test] Error 1
код: 2
```

Тест возвращает 1, а `make` при упавшей команде свой код 2.

> **Запомнить:** тест должен краснеть, когда код сломан. Проверял так: убрал `"!"` из
> `strcat(out, "!")`, и пять проверок из десяти стали FAIL. Тест, который не краснеет
> никогда, ничего не проверяет.

Где искать недостающие тесты: какие данные я бы не стал проверять, потому что «так никто не
делает». Длинное имя, пустое, кириллица, спецсимволы, буфер ровно впритык.

Тест на имя из 64 букв (ожидаю `-2`, «не влезло») на исходном коде не проходит, и
не случайно: в функции вообще нет ветки, которая возвращает `-2`. Она вернула 0 и молча
записала 73 байта в буфер на 64. Тест покраснел, но о порче памяти ничего не сказал, это
уже работа санитайзера.

## Покрытие

Компилятор с `--coverage` вставляет счётчики в каждую строку. При компиляции появляется
`.gcno` (карта строк), после запуска `.gcda` (сколько раз выполнялась каждая).
`gcov` склеивает их в отчёт `файл.c.gcov`:

```text
$ gcov -b -o build/cov build/cov/greeting.gcno
File 'src/greeting.c'
Lines executed:69.23% of 13
Branches executed:100.00% of 8
Taken at least once:87.50% of 8
```

В `greeting.c.gcov` перед каждой строкой число запусков. `-` — строку нельзя
выполнить (комментарий, скобка), `#####` — ни разу не выполнялась:

```text
        5:   20:    if (name[0] == '!') {
    #####:   22:        strcpy(out, "HELLO, ");
    #####:   23:        strcat(out, name + 1);
```

`-b` добавляет ветки: «Taken at least once 87.50%» значит одну из восьми ветвей `if` ни разу
не выбрали.

`.gcda` дописывается при каждом запуске, счётчики копятся. Поэтому цель `coverage` начинает
с `rm -rf build/cov`, иначе в отчёт попадут прогоны старой версии. И если тест упал,
рецепт `make` останавливается до `gcov`. Пока ошибка не исправлена, отчёт можно получить
через `make -i coverage` (продолжать после ошибок).

> **Грабли:** `gcov` ищет `.gcno` по имени объектного файла. В Makefile лекции объект
> называется `test_greeting.o`, а в команду передаётся `test-test_greeting.gcno`, отсюда
> строка `cannot open notes file`. На отчёт по `greeting.c` это не влияет, но путает.

Покрытие 100% не значит «ошибок нет». После теста на `"!Аня"` у `greeting.c` стало
100% строк, а переполнение на длинном имени осталось: строка `strcat(out, name)`
выполнялась, только с короткими именами. Покрытие показывает, где я не искал, и это всё.

## Санитайзеры

Флаг компилятора добавляет проверки к каждому обращению к памяти:

```bash
gcc -std=c11 -Wall -Wextra -O2 -g -Iinclude -fsanitize=address,undefined \
    -fno-omit-frame-pointer -o build/sanitize-app src/main.c src/greeting.c
```

`address` (ASan) ловит запись и чтение за границей массива, чтение освобождённой памяти,
двойной `free`. `undefined` (UBSan) ловит неопределённое поведение: деление на ноль,
переполнение `int`. `-g` нужен, чтобы в отчёте были файлы и строки. По слайдам программа под
санитайзером в 2–3 раза медленнее, поэтому его включают для проверок, а не в готовой сборке.

Отчёт читается сверху вниз:

```text
==538==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7c8e15400060 ...
WRITE of size 101 at 0x7c8e15400060 thread T0
    #0 0x7c8e18076922 in strcpy ../../../../src/libsanitizer/asan/asan_interceptors.cpp:563
    #1 0x5acd2f29d6aa in strcat /usr/include/x86_64-linux-gnu/bits/string_fortified.h:130
    #2 0x5acd2f29d6aa in make_greeting src/greeting.c:29
    #3 0x5acd2f29d376 in main src/main.c:13
...
    [32, 96) 'buffer' (line 10) <== Memory access at offset 96 overflows this variable
```

Тип ошибки (переполнение на стеке), размер записи (101 байт: 100 букв и `'\0'`), первая
строка со своим кодом (`greeting.c:29`, это `strcat(out, name)`), какой буфер пострадал
(`buffer` из `main`, байты 32…95).

Санитайзер срабатывает только там, где программа реально прошла. Под исходными тестами
он молчит: длинного имени нет, до опасного места не доходим.

> **Грабли:** без санитайзера ошибка бывает вообще не видна. `./app` с именем из 60 букв
> напечатал приветствие и вернул 0, хотя записал 69 байт в буфер на 64. Со 100 буквами
> упал с `*** stack smashing detected ***`: это защита стека, которую gcc в Ubuntu включает
> по умолчанию. Под ASan оба случая сразу дают отчёт.

## Фаззинг

Человек придумывает «нормальные» данные, фаззер тысячи случайных. Учебный фаззер:
случайная длина 0…60, символы из алфавита с `!` и пробелом, вызов функции, проверка
результата. Собирается с санитайзером, поэтому любая порча памяти сразу видна.

```text
$ make fuzz
...
./fuzz_greeting 2000 1
==610==ERROR: AddressSanitizer: stack-buffer-overflow ...
WRITE of size 30 at 0x7f36e9900040 thread T0
    #2 0x6345c90a5c5a in make_greeting src/greeting.c:29
```

Второй аргумент — зерно для `srand`. С тем же зерном те же входы, ошибку можно повторить.
Без зерна ошибка «то есть, то нет», и разбирать её невозможно. Правильный ответ фаззер не
знает, он проверяет свойства: не упало, строка короче буфера, код возврата из допустимых.

Чем отличается от тестов:

| | Тесты | Фаззер |
|---|---|---|
| кто придумывает входы | человек | генератор случайных чисел |
| что проверяет | конкретный ответ | свойства и отсутствие падений |
| сколько вызовов | десяток | тысячи |
| польза кроме проверки | документация: видно, что умеет функция | находит случаи, о которых не подумал |

Они дополняют друг друга. На лекции восемь тестов с короткими именами против 2000 случайных,
включая длинные и с `!`. У меня с зерном 1 (и с 2, 3, 42) фаззер упал на первой же попытке:
больше половины случайных длин не влезает в его буфер на 32 байта.

Свойства для фаззера лучше писать так, чтобы они не повторяли саму функцию. Для
приветствия: `strlen(out) < sizeof out`. Для функции, которая режет строку: результат
является началом исходной строки, и в нём не больше N символов. Если проверка в фаззере
написана тем же кодом, что и функция, ошибка в обоих местах совпадёт и не найдётся.

> **Грабли:** строка `фаззинг: 2000 попыток` пропала. Вывод в pipe или файл буферизуется,
> а ASan завершает программу через `abort`, и буфер не сбрасывается. В своём фаззере
> поставил `setvbuf(stdout, NULL, _IONBF, 0)`.

## Линтеры

Линтеры читают текст, программу не запускают.

```bash
cppcheck --enable=warning,style --quiet lint/issues.c
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
clang-tidy -p build lint/issues.c
```

`cppcheck` работает сразу. На учебном `issues.c` нашёл `gets`, деление на ноль и
неинициализированную `sum`. `clang-tidy` нужен `compile_commands.json` (как каждый файл
компилируется), его делает CMake. Он сказал, что `gets` вообще не объявлена: в C11 её
убрали из стандарта.

Оба по умолчанию возвращают 0 даже с замечаниями. Чтобы `make` упал, нужны
`cppcheck --error-exitcode=1` и `clang-tidy --warnings-as-errors='*'`.

Ложные срабатывания бывают. `clang-tidy` ругается на любой `snprintf` и `memcpy`
(`DeprecatedOrUnsafeBufferHandling`) и советует `snprintf_s` из Annex K C11, которых в
glibc нет. Такое правило выключается в `.clang-tidy` с комментарием, почему.

## Как починить приветствие

```c
int n = snprintf(out, cap, "Hello, %s!", name);
if (n < 0)
    return -1;
if ((size_t)n >= cap)
    return -2;   /* не влезло */
return 0;
```

`snprintf` пишет не больше `cap` байт и возвращает, сколько хотел записать. Если это
`>= cap`, строка обрезана, и функция честно говорит `-2`. После правки `make test`,
`make fuzz` и `make sanitize` зелёные.

## Кто что ловит

Неверный ответ («Hello» вместо «Hi», 41 вместо 42) ловят только тесты. Порчу памяти ловит
санитайзер, но только на пути, по которому программа прошла. Неожиданные данные (пустые
строки, огромные длины, странные символы) подбирает фаззер. Опасные места в тексте
(забытый `#include`, деление на ноль, неинициализированная переменная) находит линтер ещё
до запуска. Покрытие само ничего не ловит, оно показывает, где я не искал.

Неправильную задачу не поймает никто. Если программа делает не то, что нужно, все пять
инструментов промолчат.

## Чек-лист перед сдачей

1. Тесты есть хотя бы на главный случай и краснеют при поломке.
2. Каждая строка с `#####` либо покрыта, либо я могу объяснить, почему нет.
3. `-fsanitize=address,undefined`, и ни одного `ERROR: AddressSanitizer`.
4. Фаззер отработал тысячу попыток и не упал.
5. `cppcheck` и `-Wall -Wextra` молчат, а про оставшееся предупреждение я знаю, почему оно
   ложное.
6. Код прочитан глазами: что программа должна делать, знаю только я.
